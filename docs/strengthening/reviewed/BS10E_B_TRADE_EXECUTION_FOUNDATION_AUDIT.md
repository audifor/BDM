# BS10E-B Trade Execution Foundation Audit

Status: resolved foundation; negotiation and binding approval are not implemented.

## Scope and inspected authority

Reviewed the trade domain/engine, contract and transaction models, roster/contract repair, salary engine, GameWorld validation, season transition, responsibility and Governance registries, Trade Center, TradesWorkspace, staff recommendation acceptance, application/store action seams, and TradePackageIntelligence. BS10E-A's `TradeProposal` is an ephemeral command, `TradeRecord` is completed trade-level history, and package intelligence is derived/read-only. No persisted offer, counter, negotiation, or acceptance lifecycle exists.

## Findings by required topic

1. **Contract transfer semantics.** An active standard contract is the player's legal agreement. A trade changes the employer/team affiliation; it does not renegotiate or terminate that agreement. The truthful operation is to keep the same contract and change `teamId` to the receiving team atomically with roster movement. Releasing and recreating would fabricate contract history and could alter salary terms.
2. **Contract ID.** Preserve the same `ContractId`. PlayerTransaction references that ID, and contract terms remain unchanged. Scheduled contracts are not transferred by this execution rule: player assets require a currently active source-team contract.
3. **Salary responsibility.** Payroll selects active contracts by their `teamId` and reads the current contract-year compensation. Moving that affiliation moves ordinary salary responsibility to the receiving team without changing salary/cap-hit/guarantee schedule. Existing dead money remains separately team- and season-attributed.
4. **Retained salary.** Retention is represented by `RetainedSalaryObligation`, with player, retaining team, receiving team, season, amount, and source trade. The player's full contract moves; the retained obligation remains attributed to the former team and is separately counted by cap payroll. It is not a second contract. The current validator treats a retained amount as a cap adjustment and enforces configured limits.
5. **Roster/contract integrity.** `RosterContractIntegrity` treats a single active contract and roster membership on the same team as valid; it repairs drift only with canonical transaction evidence. It deliberately does not impose a global roster-to-contract one-to-one rule that would break rights-only, scheduled, and nonprofessional contexts. Trade execution must instead create a coherent roster/contract result itself.
6. **PlayerTransaction.** It is player-level career history; trade records are package-level history. Each moved player therefore needs a `traded` transaction with both teams and the transferred ContractId. World validation now requires these fields and verifies the contract belongs to that player.
7. **TradeRecord relationship.** One completed `TradeRecord` captures the package and the retained-obligation/created-exception references. Per-player `traded` rows reference the same unchanged player contract. The two histories answer different queries and are not duplicates.
8. **Atomicity.** `executeTrade` validates first and returns the exact input world on failure. Success assembles roster, contract, pick/right ownership, exception, retained obligation, lineup, TradeRecord, and PlayerTransaction changes in one `updateGameWorld` construction. No partial world is returned. Cash consideration has no club financial-ledger settlement, so a package with cash now fails with `CASH_SETTLEMENT_UNAVAILABLE` and returns the input world unchanged.
9. **Trade eligibility timing.** Existing `TradeRules` are season-scoped but had no date window; searched season/calendar structures and found no authoritative generic trade deadline or transaction cutoff to reuse. The implementation adds optional `TradeWindowRule` (`opensOn`, `closesOn`) within the owning season. No real-world NBA date is invented.
10. **Trade rule rollover.** Rules materialize for a successor only when the competition and ecosystem stay the same and no target-season rule exists. Rule contents are copied with the new SeasonId. An explicit season-wide window stays explicit. Dated bounds shift by the start-year delta; if the shifted interval cannot fit the target season, the window is dropped so legality fails closed. Missing source rules are not invented.
11. **Negotiation responsibility.** `tradeRecommendation` is advice. A separate `negotiatePlayerTrade` responsibility covers the future nonbinding contact/counterparty discussion. It supports user-controlled or delegated modes, with no automatic staff delegation.
12. **Execution responsibility.** `executePlayerTrade` is distinct from negotiation and recommendation; it also supports user-controlled or delegated mode, with eligible basketball leadership/cap-contract roles. A recommendation or negotiation does not imply commitment authority.
13. **Governance authority.** Player contract signing is not reused. `PLAYER_TRADE_COMMITMENT` is a distinct generic-subject Governance decision with effect-required execution policy, suitable for an exact package reference. This milestone does not create decisions or connect two clubs' approvals to a trade effect, so actual approval rights remain unknown and execution authority is fail-closed in package intelligence.
14. **User authority.** User-controlled responsibility rows represent the user's operational action for the controlled team; no artificial staff holder is required. This does not grant Governance approval.
15. **AI authority.** AI must have a delegated holder for negotiation/execution. Missing delegation remains `UNKNOWN`; this milestone assigns no staff. Both responsibilities default to `userControlled` when materialized by the existing registry conventions.
16. **Existing unsafe execution seams.** Direct Trade Center and TradesWorkspace calls were removed; Trade Center now performs read-only assessment. The Advisory Center acceptance function returns `negotiationRequired` and does not mutate state. The store/app command is removed. Staff UI communicates the unsupported state. `executeTrade` remains defined and used only by focused engine tests; no production caller remains.
17. **Exact remaining negotiation gap.** There is no durable package lifecycle, counterparty response, acceptance, per-side actor authorization, per-side exact-package Governance resolution/effect, or final command connecting an accepted package to an atomic engine execution. BS10E-C must supply these before ordinary trade execution can return.

## Boundaries retained

- Generated FIBA/NCAA seasons remain unsupported where they have no trade rules; this milestone does not add rules to them.
- Economic fairness, value, and acceptance probability remain unknown and are not computed.
- No trade negotiation, offer, counter, or acceptance entity is persisted.
- Cross-ecosystem contracted acquisition remains on the existing transfer-route requirement.
