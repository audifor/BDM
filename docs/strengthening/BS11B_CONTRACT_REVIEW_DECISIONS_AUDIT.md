# BS11B Contract Review Decisions Audit

## Scope and conclusion

BS11A supplies a derived projection. BS9 owns needs; a need means attention is warranted, not that a club wants to retain a player. The existing GM response `CONTRACT_RETENTION_REVIEW` is a persisted preference to route a need to review, not a player-level retention decision. `contractRecommendation` produces advisory staff output and has no canonical acceptance seam. The architecture supports a narrow persisted layer for explicit user intent, while autonomous AI retention intent remains unavailable until a truthful owner and acceptance/decision responsibility exist.

## Existing concepts and ownership

1. **Contract decision concepts.** `PlayerContract` has dated scheduled/active/expired/terminated states. BS9 `CONTRACT_CONTINUITY` identifies a key active player's unresolved expiry within its existing 365-day window; `CONTRACT_CLUSTER` aggregates three or more such key expiries. Neither encodes intent.
2. **Recommendation versus execution.** `contractRecommendation` and `recommendSignings` are staff recommendation responsibilities. `acceptStaffRecommendation` has canonical mutations only for medical, recruiting, and trade recommendations. Contract recommendation acceptance fails closed as `notAcceptable`. Contact, offer, and signing have their own responsibility and application boundaries.
3. **Existing GM planning.** `GMPlanState` is persisted per team and need. `CONTRACT_RETENTION_REVIEW` routes to contract review with `WAITING_INFORMATION`; it does not identify the player decision or create a successor. `WAIT_AND_MONITOR` is an existing GM workflow choice, but not an explicit contract defer date.
4. **Responsibility ownership.** `contractRecommendation` is advisory, not a retention-intent executor. `recommendSignings` concerns the market acquisition side. The explicit review command for the user's own club is USER-owned and needs no staff proxy. BS11B adds no responsibility; AI may display the same derived review facts, but does not record autonomous retention intent.
5. **User authority.** The desktop app is already wired through `DesktopAppActions` to GameStore application commands. Analysis currently receives only `world`, so a narrow callback can carry the four user choices without putting decision rules in React. A command must verify the team is controlled by `userCoachId`.

## Review and intent semantics

6. **Review eligibility.** One review candidate is derived per active `CONTRACT_CONTINUITY` need, using its canonical `contractId` evidence plus BS11A expiry context. This retains BS9 as need authority and avoids turning a `CONTRACT_CLUSTER` into one multi-player decision. Existing same-team successor suppression remains authoritative.
7. **Decision identity.** Stable identity is `teamId + playerId + current contractId`; the only current review reason is `CONTRACT_CONTINUITY`, so a separate free-form reason/horizon identity would duplicate the source need. A replacement contract has a new identity; repeated writes for the same unresolved deal upsert the same record.
8. **PURSUE_EXTENSION.** Nonbinding intent to attempt retention beyond the current term. It creates no terms, salary, negotiation, Governance request, or contract. It does not resolve the BS9 need until a successor contract actually exists.
9. **ALLOW_EXPIRY.** Nonbinding intent not to pursue a successor. The contract runs unchanged to its existing expiry; normal lifecycle reconciliation remains responsible for expiry. It does not suppress positional continuity evidence or itself release the player.
10. **REVIEW_RELEASE.** A request to consider an early exit. It neither calls `releasePlayer` nor initiates an outgoing market action.
11. **DEFER.** Persisted intent to revisit at the next actual season boundary (season end or start) for a season in which the team participates, capped at the current contract's expiry. These dates come from canonical Season records; if no later season date exists, the contract expiry closes the review. Once the revisit date arrives, the same candidate is reviewable again and the user can replace the defer decision.
12. **Resolved and stale states.** Candidate status is derived from current world truth: successor, player departure, contract termination, or expiry closes live review. A missing/stale need makes an old intent non-actionable. Explicit intent is historical state, not a cached projection. Role/strategy/finance context is refreshed in the advisory; those context changes alone do not override an explicit user decision.

## Timing, information, and subsystem boundaries

13. **Timing policy.** The current BS9 contract-need rule already defines review readiness as an unresolved key expiry within 365 days, with existing 30/90-day urgency tiers. BS11B reuses it and introduces no new arbitrary interval. This is a current product rule, even though it is day-relative rather than season-relative.
14. **Approaching-expiry checkpoint.** Material GM checkpoints do not run on ordinary calendar days. Calendar lifecycle reconciles expiry daily but does not recheck GM planning as a contract first enters the 365-day BS9 window. Add a single `IMPORTANT` (non-blocking) breakpoint when a user-team active, unresolved contract's expiry equals current date plus 365 days. This is a narrow crossing event; the live candidate remains derived and visible afterward. No daily contract-planner persistence/recompute is needed.
15. **Information boundary.** The review candidate uses own-team contract truth, BS9 needs, BS11A role/age/development/continuity/payroll context, and current strategy. It does not read hidden opponent ratings, future potential, MarketReality, external market estimates, or renewal salary demands. AI owns no intent in this milestone.
16. **RolePromise and usage.** RolePromise is market negotiation state (`ACTIVE`, `FULFILLED`, or `BROKEN`), not a retention decision. BS11A starter/rotation/rostered, age, development, continuity, and Finance schedule remain evidence only; no universal score is added.
17. **Finance.** Current/future payroll and final-year salary remain Finance/contract facts. No affordability claim about unknown terms is made.
18. **BS9 integration.** Review candidates are projected from existing `CONTRACT_CONTINUITY` need evidence. Decisions do not create needs or resolve them. A pursue intent does not claim retention is secured; allow-expiry can coexist with the continuity need and future succession evidence.
19. **BS10 integration.** Pursuit is not contact, offer, negotiation, signing, or a free-agent transaction. Release review does not create an outgoing trade/release action. BS10 remains the actual market boundary.
20. **Governance and release.** `PLAYER_CONTRACT_SIGNING` is reserved for the actual future signing/approval path. Planning intents create no Governance records. Existing `releasePlayer` immediately terminates an active contract, removes roster/lineup membership, records `released`, then rechecks planning; it enforces roster/availability floors. No contract-release Governance type or modeled severance/fee path was found. This milestone never invokes release.
21. **Breakpoint behavior.** Contract review is `IMPORTANT`, not `ACTION_REQUIRED` or `BLOCKING`; several expiries do not stop advancement. Existing SimulationBreakpoints ordering and continue behavior remain intact.

## Persistence and exact BS11C gap

22. **Persistence need.** Explicit user choices must survive save/load. Persist only one minimal intent record per deterministic review identity: team, player, current contract, intent, decision date, user coach, and (for defer) the next actual season checkpoint/expiry. Derive candidate/readiness/context on demand; do not save BS11A projection or cached review status. Add an optional Save V4 collection and default missing old saves to an empty list.
23. **Invalidation.** Projection resolves when a continuous successor appears, the player is no longer on the team, the contract expires, or it terminates. Review candidates require current `CONTRACT_CONTINUITY` need evidence. Stale decisions remain visible only as non-live history and cannot enable negotiation or release.
24. **Exact BS11C gap.** No player extension/re-sign negotiation exists. BS11C can consume `PURSUE_EXTENSION` as a negotiation trigger only after defining negotiation participants, market/agent information rules, approved term generation, salary authority and proposal flow, player response/counter semantics, separate Governance/signing, atomic contract activation, role promises, and intent cleanup on signing/withdrawal/expiry. Other intents must remain nonbinding planning until their separate actions are explicitly authorized.
