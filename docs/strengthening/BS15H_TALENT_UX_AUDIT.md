# BS15H Talent UX Audit

Audit baseline: `d71fd3d85983ae46562ac278862f4519cdee0626` (BS15G). This audit was completed before BS15H UI changes. UI consumers below read `GameWorld` through existing workspace models/components and call application/store commands; UI is not a domain authority.

## Surface inventory

| Surface / route | Current authority and actions | Missing information, actions, and blocked behavior | Navigation, duplication, truth risk, priority |
|---|---|---|---|
| Scouting — `app=scouting`, `ScoutingWorkspace` | `buildScoutingWorkspaceModel` reads discovery, organization knowledge, assignments/reports, focus candidates and territory coverage. Requests/cancels missions, changes priority, opens reports and Players, edits coverage/focus. | Assignment rows show status/workload and reports show confidence/coverage; knowledge board separates discovered from scouted. Current overview lacks a pathway-wide next action and direct Recruiting/Portal/Draft links; action availability is summarized at workspace level. | Player links use canonical `app=player&playerId=…`. No duplicate scouting screen. Model applies organization knowledge; retain this boundary. P1. |

Add a thin view over authorized canonical records and link into Recruiting; do not invent candidates or private source relationships. P0. |

No separate history authority. P1. |
| Inbox / notifications — Home dashboard inbox module | `getInboxItemsForCoach` reads canonical inbox items from world; event producers write canonical inbox records. | Inbox content is embedded in Home and talent events do not have a common attention summary; actions depend on stored item action/context. | Staff / scouting assignments | Staff workspace and Scouting assignment/coverage boards read staff roles, workload and assignments. Scouting commands enforce staff suitability/capacity. | Scouting provides assignment workload and unavailable summary, but capacity limits/alternatives are not always explained at the blocked action. | Contracts / compensation | `ContractsWorkspace`, Player contract view and compensation domains; separate contract and aid/benefit/NIL models. | Talent workflows lack one clear contextual jump to owned Player compensation/retention details. | Global navigation / search | Workspace query routes (`app`, `playerId`, `playerView`), taskbar/start menu and `navigateToPlayer`. | Scouting, Recruiting and Draft are separate apps; no Talent Operations home, Portal route, consistent subnavigation, or talent-aware search. Avoid global discovery of latent candidates. | Top/system navigation convention; add route links and a focused overview. No permanent sidebar. P0. |

## Baseline product risks

- There is no route or workspace for a Portal-first workflow despite canonical Portal state and lifecycle commands.
- There is no actionable cross-workflow overview; users must know which subsystem to open.
- Direct Player navigation exists, but shared pathway status and transition links do not connect the apps.
- Blocked reasons are uneven: Draft has a read model; Recruiting sometimes shows translated reasons and sometimes raw codes; Scouting summarizes request availability.
- Keep all hidden ratings and motivations behind the existing organization-knowledge and permitted RecruitingIntel reads. Public data may be shown independently.
