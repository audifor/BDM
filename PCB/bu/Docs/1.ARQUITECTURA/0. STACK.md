## Arquitectura completa: Electron + React + Python + SQLite + JSON (Windows offline)

### Objetivos

- Offline 100%, sin servicios externos.
    
- UI muy compleja con grid tipo Excel.
    
- Python como motor (simulación, reglas, generación de stats).
    
- Persistencia local con SQLite y JSON para flexibilidad, sin inflar tablas.
    

---

## 1) Componentes y responsabilidades

### Electron Main (Node)

Responsable de:

- Crear ventana, menús, rutas de datos.
    
- Lanzar y supervisar el proceso Python (engine).
    
- Canal IPC seguro entre renderer y engine.
    
- Logging y manejo de errores fatales.
    

### React Renderer

Responsable de:

- UI, navegación, estados visuales, grids, formularios.
    
- Lógica de presentación.
    
- Caché de datos y sincronización con engine vía un cliente IPC.
    

### Python Engine

Responsable de:

- Acceso a SQLite (único escritor).
    
- Dominio y reglas (contratos, ratings, progreso, lesiones, etc.).
    
- Simulación de partidos y temporadas.
    
- Importación y exportación (CSV/JSON).
    
- Migraciones y compatibilidad de partidas guardadas.
    

### SQLite (archivo local)

- Un fichero por partida guardada o una DB con múltiples savegames.
    
- JSON en columnas TEXT + columnas generadas indexadas para rendimiento.

## 2) Flujo de comunicación (recomendado)

### Renderer -> Main -> Engine (IPC interno)

- Renderer nunca habla directo con Python.
    
- Main gestiona el proceso y el protocolo.
    
- Mensajes JSON por stdin/stdout o por pipes.
    
- Cada request lleva `request_id` para correlación.
    

#### Formato de mensajes

Request:

`{   "request_id": "uuid",   "command": "player.list",   "payload": { "team_id": 3, "filters": { "min_age": 18 } } }`

Response:

`{   "request_id": "uuid",   "ok": true,   "result": { "items": [], "total": 0 } }`

Error:

`{   "request_id": "uuid",   "ok": false,   "error": { "code": "VALIDATION_ERROR", "message": "..." } }`

Eventos push (progreso, logs, simulación):

`{   "event": "simulation.progress",   "payload": { "percent": 42, "label": "Simulando 2026-11-05" } }`

Regla importante:

- Escrituras y lecturas de DB solo en Python. Evitas corrupción, bloqueos raros y duplicación de lógica.

## 3) Persistencia y esquema de datos

### Enfoque: pocas tablas núcleo + JSON por entidad

Tablas núcleo típicas:

- `savegame`
    
- `team`
    
- `player`
    
- `season`
    
- `match`
    
- `contract` (opcional si quieres consultas fuertes)
    
- `event_log` (muy recomendable)
    

Cada tabla tiene:

- columnas mínimas estables
    
- `data_json` para todo lo variable
    
- columnas generadas para los campos que filtras mucho
    
- índices en columnas clave
    

### Ejemplo: player

Columnas base:

- `id` INTEGER PK
    
- `savegame_id` INTEGER
    
- `team_id` INTEGER
    
- `name` TEXT
    
- `data_json` TEXT NOT NULL
    
- `updated_at` INTEGER
    

Columnas generadas (para rendimiento):

- `age` GENERATED desde `json_extract(data_json,'$.bio.age')`
    
- `pos` desde `json_extract(...'$.sport.pos')`
    
- `overall` desde `json_extract(...'$.ratings.ovr')`
    
- `potential` desde `json_extract(...'$.ratings.pot')`
    
- `salary` desde `json_extract(...'$.contract.salary')`
    
- `contract_end` desde `json_extract(...'$.contract.end_date')`
    

Índices:

- `(savegame_id, team_id)`
    
- `(savegame_id, overall)`
    
- `(savegame_id, age)`
    
- `(savegame_id, contract_end)`
    

Principio:

- Todo lo que va a un grid con filtros frecuentes debe tener columna generada indexada.
    
- Lo demás va a JSON sin culpa.
    

### Modo WAL

En engine, al abrir DB:

- `PRAGMA journal_mode=WAL;`
    
- `PRAGMA synchronous=NORMAL;`
    
- `PRAGMA foreign_keys=ON;`
    
- `PRAGMA temp_store=MEMORY;`
    
- `PRAGMA cache_size=...` según tamaño

## 4) Gestión de partidas guardadas

Estrategia sencilla y robusta:

- Un directorio por savegame:
    
    - `pcbasket/saves/<save_id>/game.sqlite`
        
    - `pcbasket/saves/<save_id>/meta.json`
        
    - `pcbasket/saves/<save_id>/backups/`
        

Backups:

- Al guardar manualmente, copiar DB a `backups/` con timestamp.
    
- En autosave, rotación de 3 a 5 copias.
    

Compatibilidad:

- `savegame.schema_version` y migraciones en Python (Alembic o migrador propio).
    
- Si sube versión, migrar al abrir.
    

---

## 5) Motor Python por capas

Estructura recomendada:

- `domain/` entidades y lógica pura (sin IO)
    
- `services/` casos de uso (crear jugador, simular partido, avanzar día)
    
- `repo/` acceso a DB (SQLAlchemy o sqlite3 directo)
    
- `sim/` simulación (partido, fatiga, posesiones)
    
- `api/` capa de comandos (mapea `command` a servicio)
    
- `migrations/`
    
- `infra/` logging, config, paths
    

Regla:

- Servicios devuelven DTOs serializables a JSON.
    
- Nunca devuelvas objetos DB al renderer.

## 6) UI compleja en React

### Estado y datos

- Caché de queries: TanStack Query
    
- Estado UI: Zustand
    
- Validación: React Hook Form
    

### Grid tipo Excel

- AG Grid si el nivel es alto (edición inline, agrupaciones, pinned columns, virtualización, etc.)
    
- Estrategia para rendimiento:
    
    - Paginación o virtualización real
        
    - Filtros server side cuando el dataset crezca
        
    - Columnas calculadas pesadas se precalculan en engine y se almacenan o cachean
        

### Patrón de pantallas

- Cada pantalla define:
    
    - `queryKey`
        
    - `fetcher` via IPC
        
    - `mutations` via IPC
        
    - invalidación de caché al guardar

## 7) Logging, errores y diagnósticos

- Python escribe logs en `logs/engine.log`
    
- Electron main escribe `logs/app.log`
    
- Un comando IPC `debug.exportDiagnostics` que empaqueta:
    
    - logs
        
    - meta.json
        
    - versión app
        
    - schema_version  
        Sin datos sensibles si no quieres.
        

Errores:

- Catálogo de códigos: `VALIDATION_ERROR`, `NOT_FOUND`, `CONFLICT`, `DB_CORRUPT`, `INTERNAL`
    
- Main puede mostrar pantalla de recuperación si engine no arranca.
    

---

## 8) Seguridad offline

- Deshabilitar `nodeIntegration` en renderer.
    
- Usar `contextBridge` y un API mínimo:
    
    - `window.pcbasket.invoke(command, payload)`
        
    - `window.pcbasket.on(event, handler)`
        
- Validación de payloads en Python (Pydantic) antes de ejecutar.
    

---

## 9) Build y empaquetado (Windows)

1. Python
    

- PyInstaller genera `engine.exe`
    
- Incluye recursos: migraciones, plantillas, datos base
    

2. Electron
    

- electron-builder empaqueta app + `engine.exe`
    
- En runtime:
    
    - Copias `engine.exe` a recursos o lo ejecutas desde `resources/`
        
    - Rutas siempre desde `app.getPath("userData")`
        

3. Actualizaciones
    

- Si vas a actualizar la app, asegúrate de:
    
    - migraciones idempotentes
        
    - backups antes de migrar
